# aihappey-ai

A multi-provider **.NET AI gateway** exposing normalized endpoints for models, media, skills, agents and MCP capabilities.

No smart routing fairy. No shiny admin portal. No hidden logic maze. No code execution.
Just provider capabilities flattened, normalized hard and exposed through open contracts.
Stateless. Boring on purpose.

Access 140k+ models and provider-native capabilities from your favorite client.

**Documentation:** https://docs.aihappey.com/gateway  
**API:** https://ai.aihappey.net

## Quick start

```bash
curl "https://ai.aihappey.net/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "openai/gpt-5.4-mini",
    "messages": [
      { "role": "user", "content": "Say hi" }
    ]
  }'
```

See the [API documentation](https://docs.aihappey.com/gateway) for endpoints, authentication, request schemas and examples.

## Run standalone on Windows

Run the gateway standalone on your own Windows machine. Download the latest standalone Windows x64 build:
[aihappey-windows-x64.zip](https://github.com/achappey/aihappey-ai/releases/download/latest/aihappey-windows-x64.zip)

Provider credentials are loaded from: `%LOCALAPPDATA%\aihappey\headers.json`  
Example: `{"X-OpenAI-Key":"sk-...","X-Anthropic-Key":"sk-ant-..."}`

Start `aihappey.Windows.exe` and use the same APIs locally at `http://localhost:5000`.

### Mammouth

Supply `X-Mammouth-Key` (or `AIServiceConfig.Mammouth.ApiKey` in the AzureAuth
sample). Mammouth uses bearer authentication at `https://api.mammouth.ai/`.
Chat Completions and SSE use `/v1/chat/completions`; Responses, Messages,
Unified and Vercel chat use the existing chat-completion adapters rather than
undocumented native endpoints. OpenAI and Vercel embeddings use `/v1/embeddings`.
OpenAI and Vercel image generation translate internally to `/v1/chat/completions`;
no separate image contract or provider image endpoint is introduced.
Native `/v1/responses` support is not established by the official API guide or
official integration source, so both Responses modes retain the existing
Chat Completions adapter rather than probing or assuming that endpoint.

Discovery reads the official, public `/public/models` catalog and exposes
`mammouth/{nativeId}`, without hardcoded model IDs or aliases. Discovery is
enabled only when a gateway API key is configured; the public catalog request
does not transmit that key. Entries are deduplicated, and the complete native
entry (including `model_info` token limits and per-token pricing) is preserved
under `mammouth` metadata. The catalog does not expose reliable task labels;
model types use the existing repository ID classifier, not a new capability
catalog. Unsupported audio/video/reranking types are not exposed. Discovery is
cached with the existing credential-scoped cache.

Provider-native request fields use the existing passthrough paths:
additional root properties for OpenAI requests, `metadata.mammouth` for Chat
Completions, and `providerOptions.mammouth` for Vercel requests. Nested options,
reasoning controls, tools and future fields are forwarded without dedicated
gateway properties. Shared adapters retain their existing validation, header
handling and streaming invariants. Native usage is preserved; no pricing or
token usage is fabricated.

Image prompts become a single user message; the native model ID and remaining
native options are forwarded with `stream: false`. Native image controls can
be supplied through the existing passthrough without gateway defaults.
The documented response is `choices[].message.images[].image_url.url`, containing
base64 image data URLs. Every returned image across all choices is translated:
OpenAI receives `data[].b64_json` (or the original data URL in `data[].url` when
`response_format: "url"` is requested), while Vercel retains original data URLs
and their actual MIME types. `response_format` is handled locally, not forwarded
as a native chat response-format parameter. Remote URLs and malformed image data
are rejected without downloading or forwarding credentials to other hosts.
Reported chat `prompt_tokens`, `completion_tokens` and `total_tokens` map to the
existing image usage fields; full native metadata and headers remain available
on Vercel responses. Explicit standard image inputs take precedence over
equivalent native fields. No image size, quality or style defaults are injected.
Image editing, streaming image generation, audio and video endpoints are not
implemented: only documented API surfaces are exposed.

Official sources: [homepage](https://mammouth.ai/),
[API documentation](https://info.mammouth.ai/docs/api-quick-start/),
[dynamic catalog documentation](https://info.mammouth.ai/docs/openclaw/),
[release notes](https://info.mammouth.ai/docs/release-notes/),
[official documentation source](https://github.com/mammouth-ai/blogdoc),
and [official n8n integration](https://github.com/mammouth-ai/n8n-integration).
Current official release notes and October 2026 GitHub activity were checked;
no service-wide shutdown notice was found. Direct website/API fetches failed
DNS resolution in this environment; official documentation source and indexed
official pages were used instead. No live authenticated API verification,
account creation or paid operations were performed.

### Narakeet

Supply `X-Narakeet-Key` (or `AIServiceConfig.Narakeet.ApiKey` in the AzureAuth
sample). OpenAI speech and Vercel speech use Narakeet's short-content streaming
API, authenticated with `x-api-key`.

Discovery calls `GET https://api.narakeet.com/voices` and exposes
`narakeet/{nativeVoiceName}`. Native names, languages, locale codes, narration
styles and other voice metadata are preserved. No voice identifiers are
hardcoded. Discovery without a key returns no entries.

Speech posts UTF-8 plain text to `/text-to-speech/{format}?voice={nativeVoiceName}`
with `Accept: application/octet-stream`. The selected model supplies the voice;
an explicit standard voice overrides it. MP3 is used when no format is supplied
because the native endpoint requires a format path component; M4A is also
supported. WAV/long-content polling and video generation are not exposed.
The provider's documented 1 KB short-content size and rate limits apply;
native limit errors are returned without a speculative local character limit.

Native query parameters pass through `providerOptions.narakeet` for Vercel speech
and additional root properties for OpenAI speech, including `voice-volume`,
`voice-speed` and future parameters. Values must be scalar and are URL-encoded;
parameters do not alter authentication headers or the API host. Standard voice
and speed take precedence when supplied; speed maps to `voice-speed`.
No synthesis speed, volume or style defaults are injected.
Language is selected by the voice; unsupported standard language and instructions
fields are rejected rather than silently ignored.

OpenAI SSE speech wraps native binary chunks as audio deltas followed by done.
Non-streaming requests collect the same audio. HTTP errors preserve status and
native response text; cancellation and empty audio fail explicitly.
Vercel metadata preserves response headers, including the native
`x-duration-seconds` (generated duration rounded up to a second), without
fabricating token usage. SSE's existing usage contract has only token fields,
so duration is not mapped to SSE token usage.
No audio transcoding or persistent state is introduced.

Official sources: [homepage](https://www.narakeet.com/),
[news and operational activity](https://www.narakeet.com/news/),
[speech API](https://www.narakeet.com/docs/automating/text-to-speech-api/),
[voice listing API](https://www.narakeet.com/docs/automating/listing-voices-api/),
[REST authentication](https://www.narakeet.com/docs/automating/rest/),
[official Node.js example](https://github.com/narakeet/text-to-speech-api-nodejs-example),
[official C# M4A example](https://github.com/narakeet/text-to-speech-api-csharp-example),
and [official duration-header example](https://github.com/narakeet/text-to-speech-api-php-example).
Direct documentation fetches failed DNS resolution in the implementation
environment; official indexed documentation and official GitHub examples were
used instead. No credentialed requests, paid operations or live synthesis
verification were performed.

### Neuphonic

Supply `X-Neuphonic-Key` (or `AIServiceConfig.Neuphonic.ApiKey` in the AzureAuth
sample). OpenAI speech and Vercel speech use the official cloud API at
`https://api.neuphonic.com`, authenticated with `x-api-key`.

Discovery calls `GET /voices` and exposes native language/voice combinations as
`neuphonic/{lang_code}/{voice_id}`. Voice names and the complete native metadata,
including tags, voice type and model availability, are preserved. No voice or
synthesis model identifiers are hardcoded. Discovery without credentials returns
no entries. The selected language and voice go directly to
`POST /sse/speak/{lang_code}`; an explicit standard `voice` overrides the selected
voice, and standard `language` overrides native `lang_code` and the discovered
language.

Native JSON fields pass through `providerOptions.neuphonic` for Vercel speech
and additional root properties for OpenAI speech. This includes `temperature`,
`sampling_rate`, `encoding` and future options. Standard text,
voice, language, speed and format take precedence when supplied. No speed,
temperature, sample-rate or output-format defaults are sent. Standard `pcm`
maps to native `encoding: pcm_linear`. The SSE endpoint documents raw
`pcm_linear` and `pcm_mulaw` encodings, not native MP3/WAV containers.
Other standard output formats, non-null native `output_format`, and unsupported
encodings are rejected before any API call, including for streaming requests.
No audio conversion is performed. Undocumented standard `instructions` is rejected.
Clients remain responsible for choosing compatible native options.

The native transport returns SSE JSON with base64 audio. Non-streaming speech
decodes and concatenates those chunks, as the official SDK does. OpenAI SSE
speech emits each audio chunk as a delta followed by done. Native HTTP and
in-band errors fail the request; cancellation and empty audio are not reported
as success. Vercel provider metadata preserves native events without duplicating
their audio. No token usage is fabricated. Default linear PCM is returned as
raw `audio/pcm`, not mislabeled as a WAV file; raw mu-law uses
`application/octet-stream` with format `pcm_mulaw`. Native sample-rate metadata is
preserved. Voice management, WebSocket agents and on-device NeuTTS are not
exposed.

Official sources: [homepage](https://www.neuphonic.com/),
[API documentation](https://docs.neuphonic.com/),
[Python SDK endpoints/authentication](https://github.com/neuphonic/pyneuphonic/blob/main/pyneuphonic/_endpoint.py),
[SSE synthesis](https://github.com/neuphonic/pyneuphonic/blob/main/pyneuphonic/_sse.py),
[SDK PCM-to-WAV wrapping](https://github.com/neuphonic/pyneuphonic/blob/main/pyneuphonic/_utils.py),
[native options and response schemas](https://github.com/neuphonic/pyneuphonic/blob/main/pyneuphonic/models.py),
[voice discovery schema](https://github.com/neuphonic/neuphonic-js/blob/main/src/voices.ts),
[SDK audio assembly](https://github.com/neuphonic/neuphonic-js/blob/main/src/tts.ts)
and [recent official cloud API benchmark](https://github.com/neuphonic/api-benchmark).
Direct website/documentation fetches failed DNS resolution in the implementation
environment; details were checked against official SDK sources instead.
No credentialed requests, paid operations or live audio-format verification
were performed.

### Tilde MT

Supply a Tilde MT access key with `X-Tilde-Key` (or
`AIServiceConfig.Tilde.ApiKey` in the AzureAuth sample). Text translation uses
`POST https://translate.tilde.ai/api/translate/text` with `x-api-key` authentication.
Chat Completions, Unified, Responses, Messages and Vercel chat use the existing
translation/chat adapters; this is not a general-purpose conversational model.
Only the latest user message is translated; its text parts are sent in order as
one native batch and the translations are joined with newlines. Historical user,
system and assistant text are not translation inputs. Tools, structured
response formats and non-text content are unsupported.

Discovery calls authenticated `GET /api/engine` and exposes running native
`Tilde` and `TildeOpen` engines as `tilde/{nativeEngineId}`. It preserves engine
names, source/target languages, domains, terminology support and native metadata.
External-vendor routes are excluded to avoid duplicating existing integrations.
No engine IDs are hardcoded; discovery without credentials returns no entries.
The model identifier selects the native translation engine. Clients must supply
a nonempty native `trgLang` through passthrough, as the official SDK requires a
target language even when selecting an engine. Choose languages supported by
the discovered engine; multilingual engines retain their native language and
domain metadata rather than being assigned an invented default direction.

Native fields pass through Chat Completions additional properties, Unified
`metadata.tilde`, Vercel chat `providerMetadata.tilde`, and Responses/Messages
additional properties or `providerOptions.tilde`. This includes the required
`trgLang`, optional `srcLang`, `domain`, `termCollections` and future options.
Standard user text and the selected engine take precedence over native `text`
and `engineId`. No translation language, domain or terminology defaults are injected.

The native text endpoint is non-streaming. Compatibility streams emit the
buffered translation followed by a finish event, not live translation tokens.
No token usage is fabricated. Native HTTP errors retain their status and body.
Document translation, terminology management and engine lifecycle operations
are not exposed. No paid calls or live credentialed verification were performed.

Official references: [API product](https://tilde.ai/translate/machine-translation-api/),

### LMNT

Discovery dynamically calls `GET /v1/ai/voice/list` and exposes ready voices as
`lmnt/{nativeVoiceId}`, including system and account voices returned by LMNT.
Names, descriptions and the complete native voice metadata are preserved;
training voices are excluded. Discovery without a key returns no entries.
The model identifier selects a voice; an explicit standard `voice` overrides it.

precedence. No native model, sampling, language or debug defaults are injected.

HTTP status and body. Response headers are preserved in Vercel metadata; LMNT's
binary endpoint does not report token usage, so none is fabricated. When neither
an explicit format nor a descriptive response content type is available, the
response remains `application/octet-stream` with an unspecified format.
Voice cloning/management, WebSockets and detailed timestamp synthesis are not
exposed. No live credentialed API verification was performed.

### TwelveLabs

Supply a TwelveLabs API key with `X-TwelveLabs-Key` (or
`AIServiceConfig.TwelveLabs.ApiKey` in the AzureAuth sample). OpenAI and Vercel text
embeddings use `POST https://api.twelvelabs.io/v1.3/embed-v2` with `x-api-key` authentication.
Discovery uses the existing static catalog: `twelvelabs/marengo3.0` and
`twelvelabs/marengo3.5`, as documented in the official SDK. No credentials are needed
for discovery; execution requires a key. No standalone model-listing API is exposed
by the official SDK.

Each input string produces a separate native request and one embedding, preserving
input order. Marengo 3.0 uses `text.input_text`; Marengo 3.5 uses
`multi_input.input_text`. OpenAI float and base64 output are supported; token-ID
inputs and `user` are not. Explicit `dimensions` maps to `embedding_dimension`.
Marengo 3.5 accepts only 128, 256, or 512 dimensions; Marengo 3.0 rejects dimension
options. These constraints also apply to native `embedding_dimension` passthrough.
Omitting dimensions preserves the provider default (512 for Marengo 3.5).

Native fields pass through embedding additional properties or
`providerOptions.twelvelabs`, including `auto_truncate`, `embedding_uncertainty`,
and nested `multi_input` options. Standardized model and input fields take precedence;
native defaults are not injected. Marengo 3.5 modality token counts are summed into
prompt/total usage. Marengo 3.0 does not report token usage. Vercel response data
preserves native responses, including uncertainty and truncation details.

This integration exposes synchronous embeddings, not streaming, video indexing/search,
analysis, or asynchronous media jobs. No live credentialed API verification has been
performed. The documentation website was inaccessible during implementation; the
official generated SDK supplied the verified API schemas and catalog.

Official references: [embedding API](https://docs.twelvelabs.io/v1.3/api-reference/create-embeddings-v2/create-embeddings),

### GigaChat

place the `.crt` file in `/usr/local/share/ca-certificates/` and run `update-ca-certificates`). The
provider uses the normal .NET/OS certificate validation; do not disable TLS certificate checks.

This integration currently supports the personal API scope and the compatible v1 chat surface; it
does not expose GigaChat embedding models or the newer v2 chat/thread contract. No live credentialed
API verification has been performed.

Models are discovered dynamically from `/models`, retaining native IDs and metadata.
Text-input/text-output entries are exposed for chat; image-output entries for image generation.
Chat supports text, image inputs, SSE reasoning/text deltas and token usage through the existing
OpenAI-compatible adapters. Responses, Messages and UI chat use the existing unified chat mapping.
Native chat options are forwarded through additional properties/provider metadata without
gateway-selected sampling settings.

Image generation and editing support the native OpenAI-compatible request/response surfaces and provider options.
The generic image surface requires base64 output; URL-only results are available through the native
OpenAI image surface instead. Edits use `/images/edits` with one or more URL/Base64 image references;
uploaded images are converted to data URLs without downloading remote inputs. Generic image requests
with `files` use editing. Native options such as `watermark` and `prompt_extend` pass through unchanged.
Use JSON `images` references with additional properties for native options; the existing shared
multipart form mapper only reads standard OpenAI fields.
Editing availability is provider/model-controlled (the official client documents SenseNova U1.5 Lite);
discovery retains native input/output modality metadata without adding model IDs or tags.
Masks, image streaming and hosted agent execution are not exposed.
Agent runtimes and skills mentioned by SenseNova are client-side components, not hosted agents.
Only the mainland China Token Plan endpoint is configured; account permissions and model availability
remain provider-controlled. No live credentialed API verification has been performed.

### ModelScope

Supply a ModelScope API token with `X-ModelScope-Key` (or `AIServiceConfig.ModelScope.ApiKey`
in the AzureAuth sample). The integration uses the global API-Inference endpoint at
`https://api-inference.modelscope.ai/v1` with bearer authentication.

Models are discovered dynamically through `/models`; their native IDs and returned metadata are
retained, and entries declaring image-generation tasks are exposed as image models. Chat
completions and streaming use `/chat/completions`, forwarding provider-native request properties
through the existing additional-properties mechanism. Image generation uses `/images/generations`
in async mode, polls the documented task endpoint, and converts returned image URLs to base64
data URLs for the existing image APIs. Responses, Messages and UI chat use the existing
chat-completions mapping. Other provider surfaces are not implemented. No live credentialed API
verification has been performed.

### Leonardo.Ai

Supply a Leonardo API key with `X-Leonardo-Key` (or `AIServiceConfig.Leonardo.ApiKey` in the
AzureAuth sample). Leonardo models are discovered dynamically from the v1 platform-model listing.
Image generation uses the v1 generation and polling endpoints; Leonardo-specific request options
are forwarded from `providerOptions.leonardo`. Generation results are downloaded and returned as
base64 image data, and the raw creation/result responses are retained in `providerMetadata`.
Chat Completions, Responses, Messages, and UI chat use the existing unified image adapters, which
return once generation completes rather than streaming provider output. Image editing, video,
speech, transcription, embeddings, reranking, and decisions are not implemented. No live
credentialed API verification has been performed.

### IBM watsonx.ai

Supply an IBM Cloud IAM API key with `X-WatsonX-Key` (or `AIServiceConfig.WatsonX.ApiKey` in the
AzureAuth sample) and configure the regional watsonx endpoint in `AIServiceConfig.WatsonX.Endpoint`.
The API key is exchanged for an IAM bearer token for each request; credentials and access tokens are
not persisted. Models are discovered dynamically from
`/ml/v1/foundation_model_specs` with IBM's `function_text_chat` filter, retaining native IDs and
model metadata.

Chat and streaming use IBM's `/ml/v1/text/chat` and `/ml/v1/text/chat_stream` endpoints with
`version=2024-05-31`. Responses, Messages, and UI chat use the existing unified chat mapping.
Provider-native parameters, including the required `project_id`, are forwarded through existing
additional-properties/provider-metadata mechanisms. Only chat surfaces and model discovery are
implemented. The regional endpoint and project ID must be supplied; no live credentialed API
verification has been performed.

Official references:
[list foundation models](https://dataplatform.cloud.ibm.com/docs/content/wsj/analyze-data/fm-api-get-models.html?context=wx),
[chat API](https://www.ibm.com/docs/en/watsonx/saas?topic=code-chat),
